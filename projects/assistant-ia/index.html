// Overview

What it is, and why I built it

PHOSBOUCRAA receives internship applications by email and on paper. Someone then reads every CV, guesses which department might suit each student, and allocates places by hand. It is slow, it is subjective, and because each decision is taken in isolation, the overall result is rarely the best one available.

This platform automates the whole chain. A candidate applies through a public portal; the CV is parsed and profiled automatically; every candidate–offer pair is scored on semantics, skills and education level; and the assignment is then solved globally — the Hungarian algorithm maximises the total quality of the cohort rather than greedily taking the best match for whoever is processed first. Every proposal carries its score breakdown, so a recruiter can see exactly why it was suggested and accept or reject it.

It was my final-year engineering project, and I wanted it to survive contact with reality rather than stay a demo: real authentication and row-level security, background jobs, a document knowledge base, and two complete deployment targets — a full Docker stack for on-premise, and a zero-cost serverless build that runs the same product on free tiers.

// Key features

What it actually does

Six capabilities carry most of the value.

CV ingestion & NLP profiling

PDF and DOCX are parsed, then profiled with spaCy plus a skills gazetteer, or an LLM when a key is configured. Skills, education level, field of study and institution are extracted, and the profile is embedded into pgvector for semantic search.

Global optimal assignment

Offers expand into capacity slots, a 1 − score cost matrix is built, and linear_sum_assignment solves it. The result maximises total cohort fit, a measurably better outcome than matching candidates one by one.

Explainable scoring

Every proposal exposes its components — semantic similarity, skill coverage, education fit — with the matched and missing skills named. Recruiters accept or reject with the reasoning in front of them, never a bare number.

RAG assistant

A tool-calling agent answers HR questions in French or English over candidates, offers, bookings and uploaded policy documents. Replies stream over SSE, tool calls are announced live, and every claim is grounded in a cited source.

Capacity forecasting

An XGBoost model projects next month's demand per department and recommends how many places to open, turning intake history into a planning signal instead of a backward-looking report.

Candidate portal

Applicants submit a CV, follow the analysis status live, see their extracted profile, and can request an offer swap by uploading proof of agreement, approved atomically so two swaps can never oversubscribe a place.

// How it works

From uploaded CV to validated assignment

Five stages. Everything heavy runs off the request path, so an upload never blocks on model inference.

  1. Intake

    The candidate submits a CV through the public portal. The file lands in object storage and a background job is queued, so the HTTP response returns immediately.

  2. Parsing & profiling

    A worker extracts the text, pulls out skills, education level and institution, normalises them against a shared taxonomy, and writes a semantic embedding into pgvector. The UI polls the status live.

  3. Pairwise scoring

    Each candidate–offer pair is scored 0.5·semantic + 0.35·skills + 0.15·education, with the weights adjustable from the interface so a recruiter can bias toward skills or toward academic level.

  4. Global optimisation

    Offers expand into one column per available place, the cost matrix 1 − score is solved with the Hungarian algorithm, and the assignment that maximises total fit is returned as a set of proposals.

  5. Human validation

    Nothing is final until a recruiter confirms it. Confirmation is capacity checked in SQL, so an offer can never be overfilled, and the candidate is notified by email.

// Challenges

What was hard, and what I took from it

The interesting problems were not the algorithms. They were the failures that stayed quiet.

Shipping the same product twice

The platform runs either as a full Docker stack or as serverless functions on free tiers — two scoring engines, one in Python, one in TypeScript. They drifted almost immediately.

The fix was a shared fixture file of golden score vectors that both test suites assert against. Changing a scoring rule now breaks both suites until both implementations agree, which is exactly the pressure you want.

Retrieval belongs in the database

The first search implementation pulled every candidate row, CV text included, into the function and filtered in JavaScript. It worked on twenty rows and would have quietly truncated at a thousand.

Moving it into Postgres as a weighted tsvector with trigram name matching cut the transfer to the rows actually needed, and let ranking use real term weighting instead of counting substring hits.

Failures that degrade silently are worse than crashes

An LLM provider was misconfigured for months. Every call raised ImportError, every call was caught and logged as a warning, and the system fell back to templated answers while still reporting a working model.

I now separate configuration errors from transient ones. A network blip may degrade gracefully; a missing dependency must fail loudly at startup.

A relevance score has to mean something

Document search normalised each result against the best hit in its own set, so the top match always displayed "100% relevant" even when it was unrelated. The number looked authoritative and carried no information.

Switching to an absolute rank made scores comparable across queries and made a minimum-relevance threshold possible, which is what stops weak passages reaching the model in the first place.
