// Overview

One platform for drivers, lot owners and the city

AutoPark is a parking-management platform built for Laâyoune, Morocco. Drivers open a mobile app, see every car park and public-street parking zone on a live map, pick an exact spot and reserve it — while lot owners, city technicians and administrators each get their own tools on top of the same data.

I built it because finding parking in the city centre is still guesswork: drivers circle the block, owners have no visibility on occupancy or revenue, and street parking is hard to enforce. I wanted to solve that end to end — not a single screen, but a real system with multiple user roles, business rules and analytics.

The result is three apps sharing one API: a Flutter app for drivers and technicians, a React portal for administrators and owners, and a Node.js/Express backend on MongoDB. The interface is in French, prices are in Moroccan dirhams (MAD), and the maps run on OpenStreetMap.

// Key features

What it does

Live parking map

Every car park is plotted on OpenStreetMap: blue pins for private lots and gold pins for public-street parking. Tap a pin for free spots, hourly price and a one-tap Reserve button.

Spot-level booking

Drivers pick an exact spot from a colour-coded grid. The API reserves it atomically, so a spot can’t be booked twice. Stays are billed per started hour, a countdown ring tracks the active booking, and cancelling costs 20%.

Four roles, two apps

Drivers and technicians use the Flutter app; admins and lot owners use the React portal. JWT auth and a role-guard middleware protect the API, mirrored by role-based redirects on both clients.

Analytics dashboards

MongoDB aggregation pipelines compute revenue per month, bookings by weekday, peak hours, occupancy and the best and worst lots — charted with Recharts for admins and owners.

Loyalty & rewards

Each completed stay adds to a per-driver, per-lot counter. Rewards such as a free booking, a car wash or a shopping voucher unlock at set thresholds, with progress bars in the driver’s profile.

Enforcement & complaints

Technicians review public-street spots alongside their active bookings and issue fines by licence plate. Owners see stays that overran their end time, and driver complaints are tracked through to resolution.

// Challenges & lessons

What went wrong, and what I learned

Reservations failed on a standalone database

The booking flow relied on multi-document MongoDB transactions, which only work on a replica set. On a standard single-node MongoDB, every reservation returned a server error. I redesigned the write around one atomic conditional update plus a compensating rollback if the booking insert fails.

What I learnedAtomicity doesn’t always require transactions — check what your infrastructure actually guarantees before depending on a feature.

A query that allowed double-booking

Fixing the first bug exposed a hidden one. Filtering spots.spotNumber and spots.status separately let MongoDB match two different array elements, so a reserved spot could be booked again — and the wrong spot got flagged. $elemMatch forces both conditions onto the same spot.

What I learnedTest edge cases with real requests against the running API, and expect one bug to be hiding another.

One API, two very different clients

React and Flutter handle state, navigation and token storage in completely different ways. Keeping sessions and roles consistent meant defining the API contract first, then mapping it to Zustand and Axios interceptors on the web and Provider and go_router redirects on mobile.

What I learnedA clear API contract and role model up front make a multi-client product far easier to evolve.

Maps and mobile lifecycle gotchas

I moved both clients to OpenStreetMap to avoid API keys and billing, and fixed Flutter crashes caused by calling setState after a widget was disposed and by navigating from inside a dialog.

What I learnedGuard every async UI update with a mounted check, and prefer open data for location features when you can.

Next steps: automated integration tests for the booking edge cases, online payments, push notifications for overstays, and a public deployment.
